# 性能与资源占用评估（macOS + Windows）

- 评估对象：qka 0.2.1（`VERSION` = 0.2.0，安装包 0.2.1）
- 测量时间：2026-11-13 14:57-15:20
- 测量机：macOS 27.0.1 / Apple Silicon；Windows 无实机
- 关联工单：`.scratch/wayfinder/map-performance.md`（qka-030 ~ qka-035）
- 明细证据：`.scratch/wayfinder/research/perf-*.md`

---

## 一、结论

**一句话**：QKA 的主要成本不在 Go 业务逻辑，而在「5 个常驻 Bun 进程 + 永远不销毁的 WebView + 每次都全量做的周期任务」这三件事上；Windows 的 80MB 里 67.6% 是内嵌的 Bun，而它换来的 4 个适配器进程本机实测零工作。

| 指标 | 现状 | 优化后可达 | 依据 |
| --- | --- | --- | --- |
| macOS 空闲 CPU | **3.2%**（90s 窗口）/ 2.9%（60s 窗口） | 1.5-2%（估） | 两个实例实测 |
| macOS 常驻内存 | 主进程 **65-72MB** + Bun **54-87MB** ≈ **120-160MB** | **约 86-103MB** | 实测 RSS + 删 4 个空闲 adapter |
| Windows 安装包 | **80.7MB**（amd64）/ **74.2MB**（arm64） | **75.4 / 69.3MB** | PE 节表 + zstd 实测 |
| Windows 首次安装写盘 | **约 197MB**（复制 80MB + 解压 116MB） | 约 190MB（结构不变则降不下来） | 代码路径 + 字节数 |
| macOS 磁盘 | `~/.qka` 64MB，其中 **59MB 是历史安装包** | **< 3MB** | 实测 |
| 稳定态磁盘增长 | 约 60-70KB/天 | 不变（已很小） | DB 页统计 |

**三个最值得先做的改动**（都小、都可回滚）：

1. 去掉 4 个空转的 Bun adapter 进程 → 省 **约 33-55MB 常驻内存**（4 个进程实测 RSS 8.2-13.8MB/个；本机 8 条数据源全是 `plugin:*`，这 4 个进程零工作）。
2. 给悬浮球/速度环接上已经写好但没人调用的 `idle()` → 窗口开过之后不再 60fps 空转。
3. macOS 构建补 `-s -w` → 二进制 **-9.15MB**、DMG **-7.6MB**；Windows zstd 从 L3 提到 L11 → **-5.29MB**。

## 二、测量方法与边界

**做了**：`ps`/`top` 采样、`sample` 调用栈分析、60s/90s 两段 CPU 时间差、磁盘与 WAL 字节统计、源码逐路径核对、`go build` 加/不加 `-s -w` 的产物体积对比、Windows exe 的 zstd 帧解码与 PE 节表拆解。

**没做（受环境限制，报告中已逐条标注）**：

- `powermetrics`（需 sudo）→ 无法给出真正的**能耗**与 **wakeups/s**，本报告里的 CPU% 是用户态时间占比，不等于功耗。
- `footprint -p`（需 sudo）→ WebKit 的 WebContent/GPU/Networking 是共享 XPC 服务，**无法精确归属到 QKA**，所以"常驻内存"是主进程 + 子进程的可归属部分，真实占用更高。
- **Windows 全部结论均无实机验证**，按置信度标注：**A** = 有制品或代码硬证据；**B** = 代码推断；**C** = 经验值。

**一处已推翻的中间结论**：初版归因认为"菜单栏状态项重绘占空闲 CPU 的 60-65%"。复核两次采样后推翻——`_updateReplicants` 在 8 秒窗口里只出现 **3 次**，主线程非等待帧占比仅 **约 0.4%**，不足以支撑该结论。真实归因见 §3.2。

## 三、macOS 实测

### 3.1 常驻资源

| 进程 | 数量 | RSS | 说明 |
| --- | --- | --- | --- |
| `qka` 主进程 | 1 | 98-130MB（ps）/ **65-72MB**（physical footprint，更准） | 23-25 线程、83 个 fd |
| `bun provider-host.js` | 1 | 21-31MB | 承载 13 个供应商插件（进程内多路复用） |
| `bun index.mjs` | **4** | 各 8.7-14MB | 4 个随包适配器，**各 1 进程** |

- 裸 Bun 底噪实测 **10.0MB**，零插件 host **19.6MB** → 87MB 里约 **50MB 是"多开一个 bun 就多 10MB"的固定税**。
- 83 个 fd 中 **15 个是 5 个子进程的 stdio 管道**。
- 这 4 个 adapter **不随供应商/账号增长**（按适配器包数线性），但**无空闲退出、无崩溃重启、无上限**。
- 每 2 小时的 `task-run` 会**再复制一整套**，峰值 **10 个 Bun 进程**，实测持续约 4 分钟。

### 3.2 空闲 CPU：3.2% 是确定的，但归因没收敛

**确定的部分**：两次独立测量（旧实例 60s：1.74s → 2.9%；新实例 90s：2.88s → 3.2%），`top` 瞬时 2.0-4.7%。**这是一个常驻菜单栏应用不该有的量级**。

**没收敛的部分**：`sample` 的 top-of-stack 显示进程绝大部分时间在等待（`__psynch_cvwait` 106,569、`mach_msg2_trap` 19,663、`__workq_kernreturn` 15,847 个样本），主线程非等待帧只占 0.4%，且其中的大头是 WebKit IPC 而不是自家代码。**没有单一热点**——CPU 分散在大量短小的周期性任务里，1ms 采样抓不到成片堆栈。

**因此**：下面的周期工作量表是**确定性事实**，但"每项各占几个点"需要 Instruments 复测（§8.1）。

| 触发源 | 频率 | 每次做什么 | 可疑度 |
| --- | --- | --- | --- |
| `monitorTokenSpeed` | 500-750ms | 调 `Snapshot()`（两次 slice 拷贝）+ **`json.Marshal` 整个快照** + 读设置 + 拼菜单栏字符串 | **高**（每 500ms 一次全量序列化） |
| tokenspeed 轮询 | 2s（空闲） | 对 **22 个文件无条件 `open`**（`service.go:533` 附近缺 size/mtime 快路径） | **高**（确定性浪费） |
| tokenspeed 重扫 | 3s | `WalkDir` 约 **1600 文件 / 960 目录** | 中 |
| 状态投影轮询 | 10s | 约 **25 条 SQLite 查询**（8 账号） | 低-中 |
| 菜单栏 `SetLabel` | 内容变时 + 每 **10s** 强制补写 | AppKit 状态项重排 | 低（实测 3 次/8s） |
| 日志清理 / 更新检查 | 1h / 6h | 可忽略 | 低 |

### 3.3 内存：窗口一旦打开就永久常驻

Wails 窗口一律 `Hidden: true` 创建，`WindowClosing` 被 cancel 后只 `Hide()`、**从不 `Destroy`**。所以 `main` / `settings` / `panel` / `petmini` / `ballPanel` / `ballMenu` **打开过一次就永久占内存**，每多一个就多一份 WebKit 渲染上下文和线程。

工具里 27 条线程中有 3 条 `CVDisplayLink`，但复核发现它们的 CPU 帧数接近 0、寿命只有 0.07-0.37s——**不是常驻 60Hz**。真正的 60Hz 在 WebContent 进程里，见下一条。

### 3.4 两个"写了但没接上"的 60fps 源头

- `assets/orb-agent-speed.js:926` 的 `setState` 末尾**无条件 `start()`**，`main.html:5414` 加载即 `setState({value:0, immediate:true})` → **主窗口/悬浮球一打开就是 60fps**，跑 WebGL 着色器 + 每帧全画布 2D clear。
- 文件里 **`idle()`（:991）全仓库没有任何调用点**——死代码；`stop()` 只在 `smooth:false` / `setLevel(0)` / `destroy()` 三条路径上。
- **性能模式有缺口**：`perf-low` 关掉了毛玻璃/阴影/transition、把 3D 宠物限到 20/30fps，但 `orb-agent-speed.js` 里**没有任何 `performanceLow` 引用**，软件渲染下球体照样 60fps；`infinite` CSS 动画与 reduced-motion 也不受它管。

### 3.5 启动期前端负载

- `main.html` **345KB 单文件**（无打包、无压缩），`panel.js` 85KB。
- `main.html:3351` 与 `panel.js:28` **静态 import** `pokemon-3d.js` → 即使不看宠物页也要解析 **888KB vendor**（three.core 381K + three.module 339K + GLTF 115K + BGU 36K + Draco 17K）。
- 主窗口还在 `main.html:8298` 直接建 3D 视图，拉 **541KB GLB + 763KB Draco 解码器** → 主窗口首载合计 **约 2.5MB**。
- 速度页每 tick（200-750ms）`innerHTML=""` + 逐个 `createElement` **全量重建** sources 与全部 session 行（`main.html:5576`），展开态每 tick 丢失。

### 3.6 磁盘

| 项 | 实测 | 判断 |
| --- | --- | --- |
| `updates/QKA-0.2.0-arm64.dmg` | **61.4MB** | **每次更新都留一份，永不清理**——安装脚本只 `rm -f "$0"`，dmg 与 `staged.json` 留着 |
| `qka.db-wal` | 4.0MB | **正常**。4,173,592 = 32 + 1013×(4096+24)，正好在默认 `autocheckpoint=1000` 页阈值上；`journal_size_limit=-1` 所以只复用不收缩，是历史高水位 |
| `qka.db` | 788KB | 正常 |
| `provider-auth.tmp.json` | 20KB | 残留，无清理 |
| `runs/run_items/quota_readings/activity_runs` | 11 天 1,914 行 / 约 496KB | **无保留期**，只增不减 |

**稳态增长约 60-70KB/天**（DB 40-50KB + 日志 20KB）。`updates/` 一次更新 ≈ 1000 天的稳态增量。

### 3.7 写放大：刷新 UI 会全量写库

`providers.List()` 每次都会把 **20 个 provider 全列 upsert**（单行 `models_json` 最大 15.8KB，整表 82KB/20 页），每个账号再加 2 次 upsert → **一次刷新约 22 个写事务、约 80KB 页写入**。实测 20 行 `updated_at` 完全相同，证明**零变化也在重写**。

### 3.8 二进制体积

`/Applications/QKA.app/Contents/MacOS/qka` = **33,559,264 B（32.0MB）**，**未 strip**（`Makefile` 的 darwin 目标只有 `-trimpath` + `-X`，`-s -w` 只加在了 Windows CLI 目标上）。同一份源码加 `-ldflags "-s -w"` 后为 **24,600,546 B**，省 **9.15MB（-27.1%）**，其中 `__DWARF` 7.50MB + `__LINKEDIT` 1.63MB；`__gopclntab` 保留，**panic 栈不受影响**。DMG 同内容镜像 60.15MB → **52.56MB**。

## 四、Windows（无实机）

### 4.1 80MB 里是什么（置信度 A，PE 节表 + zstd 帧解码）

| 组成 | amd64 | 占比 |
| --- | --- | --- |
| `bun.zst` | **54.55MB** | **67.6%** |
| Go / PE | 25.87MB | 32.0% |
| 前端资产 | 5.9MB | 7.3% |
| provider-plugins | 0.32MB | 0.4% |
| adapters | 0.005MB | ~0 |
| 对齐/其他 | 837B | — |

arm64 74.25MB = Bun 49.39MB（66.5%）+ Go 24.53MB（33.0%）。**Bun 是预编译 PE（PE symbols=0，macOS 版无 DWARF），strip 无收益。**

### 4.2 首启与升级写盘（A）

- `runtime/` 稳态 **2 × 111MB**（两代版本共存）。
- 每次升级首启再写 **116MB**；**首启总写盘约 197MB**（复制 80MB 带 fsync + 解压 116MB）。
- 崩溃残留的 `.staging-*` 目录**永不被清理**（最多 116MB）；更新失败在安装目录留 `.old` + `.failed` 各约 80MB，**只在下一次更新开头才清**。

### 4.3 常驻内存（置信度 C，需真机校准）

球窗启动即建、`WindowClosing` 被 cancel、主窗关闭只是 `Hide` → 稳态 **2 个 WebView2**；把设置/面板/宠物/右键菜单点过后最多 **6 个 renderer 全常驻不回收**。经验估算：托盘形态 **150-250MB**，主窗开过 **300-450MB**。

### 4.4 渲染（A）

悬浮球 60fps **永不停止**——和 macOS 是同一个 `orb-agent-speed.js`、同一个没人调用的 `idle()`。只要收到过一次 `tokenspeed-changed`，透明置顶球窗就**永久 60fps 重绘**。

### 4.5 其他

- 制品**未签名**（`Get-AuthenticodeSignature` 预期 NotSigned，Certificate Table=0）→ 每次下载都会被 SmartScreen/MOTW 拦一次；这是体验问题不是性能问题，但和"每版 80MB"叠在一起放大更新摩擦。
- 更新下载**无 Range 续传 + 3 次全量重下**（最坏 243MB）；服务端滴流时"不限总时长"意味着**没有上限**。

### P2（战略级，先讨论）

- **Windows 去 Bun 内嵌**：exe 可降到约 **26MB**，但破坏"单文件离线"语义；或换 Node（node.exe 压缩后 27.36MB，比 Bun 省 21.9MB，但要移植 `Bun.spawn` / `Bun.$` 宿主层，插件本身只用 `node:*`）。
- **业务表加保留期**（`runs` / `run_items` / `quota_readings` / `activity_runs`）。
- 引入性能门禁：CI 里跑 `-s -w` 体积断言 + 一次空闲 CPU 基准。

## 七、明确不做

- **UPX 压缩**：上限约 -15MB，杀软误报与启动解压开销不划算。
- **adapter 多路复用到一个进程**：能省内存，但牺牲崩溃隔离——provider-host 已经是"一进程多插件"，adapter 侧不做。
- **Bun `-baseline` 变体**：同尺寸，无收益。
- **靠删插件文档瘦身**：全部文档只 225KB，去掉省 82KB，不值。

## 八、验证计划

### 8.1 归因补测（macOS，需 sudo，一次即可）

```sh
sudo powermetrics --samplers tasks --show-process-energy -i 1000 -n 30 | grep -A3 qka
# 若可用：
sudo footprint -p <pid>
```
目标：把 3.2% 拆到具体线程/唤醒源，确认 §3.2 里"tokenspeed 轮询"与"快照序列化"各占多少。

### 8.2 每项改动的验收口径

| 改动 | 验收 |
| --- | --- |
| P0-1 | `pgrep -f index.mjs` 为空；完整签到一次仍成功；`ps` 总 RSS 下降 ≥50MB |
| P0-2 | 开窗→关窗→静置 5 分钟，球窗 CPU < 1%；`sample` 里 `frame` 不再出现 |
| P0-3 | `ls -l` 产物 ≈ 24.6MB；`go test ./...` 通过；故意 panic 一次确认栈完整 |
| P0-4 | exe ≤ 75.5MB（amd64）；解压后运行正常 |
| P0-5 | 更新一次后 `~/.qka/updates` 为空；回滚仍可用 |
| P0-6 | 静置 10 分钟，`sudo fs_usage -w -f filesys qka` 里 `open` 次数接近 0 |

### 8.3 Windows 真机必测（5 条）

1. 首启耗时 + 进程峰值 Private Bytes，证伪/证实"全量读内存"。

## 十二、决策：P1-1（窗口关闭 Destroy）不做

**2026-11-13 用户拍板：不修。** 记录结论与依据，避免后续重复讨论。

### 实测数据（本轮测量，新构建二进制）

| 场景 | 主进程 RSS | WebContent 进程 | WebContent RSS |
| --- | --- | --- | --- |
| 仅托盘（无窗口） | 121MB | 0 个 | — |
| 主窗口显示 | 139MB | 1 个 | 121.5MB |
| 菜单栏面板显示 | 146MB | 1 个 | 122.6MB |
| 面板 Hide 后 20 秒 | — | **仍存活** | 73.5MB |

结论：**每个 WebView 窗口都常驻一个约 74-122MB 的 WebContent 进程**，`Hide()` 不会释放它，只会让 RSS 从约 122MB 降到约 74MB。

### 为什么不做

1. **改造成本与风险不匹配收益**。Wails v3 的 `Window.Close()` 会触发 `WindowClosing` 钩子；当前所有窗口的钩子都是 `event.Cancel() + Hide()`（主窗口、面板、迷你宠物、右键菜单、悬浮球各一处）。要销毁就得逐个改钩子、补 `a.main = nil` 之类的指针清理、并处理「销毁后 `GetByID` 拿不到 → 必须重建」的路径（`mainWindowAlive()` 已有雏形，但其余窗口没有）。
2. **重开有可见冷启动**。窗口销毁后重开要重新加载整页：`main.html` 是 345KB 单文件，还要重跑首屏数据（供应商列表在冷启动时实测约 0.8s）。面板是「点一下菜单栏图标」的高频交互，重开变慢的体感代价高于省下的内存。
3. **高频窗口不适合销毁**。菜单栏面板、迷你宠物、右键菜单都是「点开-收起」型交互，一天可能几十次；每次销毁重建等于把这些交互都变慢。真正低频的只有主窗口。
4. **真正的内存大头已解决**。P0-1 去掉 4 个常驻 Bun 进程已省约 33-55MB；WebContent 的 74-122MB 是 WebView 架构固有成本，除非改技术栈（原生 UI）否则无法消除。

### 若将来要重新考虑

只对**主窗口**做销毁（它是低频窗口），面板/迷你宠物/右键菜单保持 `Hide`。验收口径：关闭主窗口后 `com.apple.WebKit.WebContent` 进程数下降 1；重开主窗口耗时可接受（建议 < 1s）；`a.main` 指针置空且 `ensureMainWindow` 能重建。

## 十三、Windows 版字体可读性修复（2026-11-13）

### 根因（不是「单一无衬线」）

界面本来就分 Sans / Mono 两类字体，问题出在 **Windows 上字重无法精确渲染**：

| 环节 | macOS | Windows |
| --- | --- | --- |
| 命中字体 | `-apple-system` → SF Pro / 苹方 | 前 4 个字体名都不存在 → Segoe UI → 微软雅黑 |
| 字重能力 | SF Pro 是**可变字体**，任意字重精确 | 微软雅黑只有 **400 / 700 两档** |
| 560 / 620 / 650 等 | 精确渲染 | 被浏览器**向上取整成 700** |

界面里有 **87 处**非标准字重（560/620/650/680/720/760 等）。在 Windows 上它们
全部坍缩成 700，于是「中等强调」的正文、标签、按钮全变成粗体——整屏又粗又糊。

次要因素：`-webkit-font-smoothing: antialiased` 只对 macOS 生效，Windows/WebView2
上是空声明；小字号（8.5-10.5px）在 ClearType 子像素渲染下发虚。

### 修复

1. **内嵌 Noto Sans SC 可变字体**（SIL OFL 1.1）：
   - 完整字体 14.4MB → 按界面实际字符子集化到 **433KB**（2472 字形）。
   - 可变 `wght` 轴 100-900，任意字重精确渲染。
   - 子集比 4 个静态档（844KB）还小一半。
2. **字体栈首位放内置字体**，系统字体保留兜底（缺字自动回退，不出方框）。
3. **字重收敛到 4 档**（400/500/600/700），87 处全部改完。
4. **Windows 小字号下限抬到 11px**（`html.platform-win32`，只影响最小三档）。
5. **标注 `-webkit-font-smoothing` 仅 macOS 生效**，避免误以为调过渲染。

- `internal/gui/frontend/assets/fonts/noto-sc-vf-subset.woff2`（433KB）
